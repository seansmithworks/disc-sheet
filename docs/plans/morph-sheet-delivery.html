Detail

1. Motion presets — the shape, and why the obvious version fails

A preset is an object passed to a new preset prop on Root, not a string: 

import { MorphSheet, presets } from "@seansmithworks/morph-sheet";

<MorphSheet.Root preset={presets.snappy}>

The obvious version — exporting spring objects for the existing transition prop — cannot work. Your tuner exports four fields (discShell, avatar, leadDelay, avatarFill) and MorphTransition has exactly three keys. It would round-trip half a preset. A preset object carrying {transition, surfaceCloseLeadDelayMs, sharedSize} reaches all four.

A preset="snappy" string union is also wrong: zero of Radix, Base UI, Vaul, Ark and Headless ship named presets, and a string union makes every name a permanent compatibility promise with a lookup table behind it. Exported objects are tree-shakeable, spreadable, and deletable.

Also in this item: accept Motion's {visualDuration, bounce} as a Spring alternative to {stiffness, damping, mass}. Two numbers that mean what a designer thinks they mean. Your tuner's own baseValues already store springs this way.

Risk is M because it touches the transition merge path. The mitigation is that default must produce byte-identical output to today, and the 75-test geometry gate proves it.

2. Tuner into this repo — two halves

(a) Versioned copy for you. Move /tune out of ~/Code/_experiments/disc-sheet-consumer (which has no git) into example/, runnable from an npm script. Today the only durable record of it is a JSON snapshot of its localStorage.

(b) Copy-in for consumers. npx morph-sheet add tuner, reusing the tested add machinery in bin/morph-sheet.mjs. Already the decided delivery path, for good reasons: dialkit pulls Geist Mono from Google Fonts, so as a dependency it would put an external font request in every consumer app forever, and a tuning panel reachable from a production bundle is a footgun.

3. The "why would I want this" example

An app icon that morphs into an App Store-style preview card with real media in it. This is your own idea from the backlog and it is the right one: it shows a use nobody would derive from a contact card, and it doubles as the site page's hero and the launch post's demo.

Depends on nothing else in this list. Could run in parallel.

4 & 5. The two traps

"use client": the namespace-property access is unresolvable server-side and the resulting error does not say so. A dev-only runtime check that throws with the actual fix in the message costs almost nothing and removes the most likely first-run failure.

motion peer: run the geometry suite against v13. Either it passes and you widen the peer honestly, or it fails and you have found a real bug before a stranger did. Right now the peer range claims support for a version nothing has tested.

Why shape variants are cut

A shape dial without child-radius masking ships a control whose every non-circle setting looks broken: the trigger surface goes squircle while the shared content stays round. That is a bug you already hit once by accident.

Doing it properly means the shared content masks to the animated radius mid-morph, not the static token. A true iOS squircle is a superellipse; border-radius only approximates it, and clip-path does not interpolate through the FLIP the way the radius MotionValue does.

It is the largest item you named and the only one that can regress motion you have already approved. It is a good 0.2.
